# P0: периодические 503 на dockentra.ie — диагностика (19 октября 2026)

Только диагностика: код, конфигурация и аккаунты не менялись. Источник данных — живые логи production Worker (`wrangler tail`) во время контролируемых запросов, код OpenNext 1.20.6 / Next 16.3.4 в `node_modules`, ответы сайта.

## Конфигурация (ПРОВЕРЕНО)

| Что | Значение |
|---|---|
| Next.js / OpenNext Cloudflare / Wrangler | 16.3.4 / 1.20.6 / 4.131.1 |
| Middleware / proxy | нет |
| Кэш страниц | KV (`NEXT_INC_CACHE_KV`), тег-кэша нет |
| Пересчёт устаревших страниц | `memoryQueue`: HEAD-запрос Worker'а к самому себе через `WORKER_SELF_REFERENCE`, таймаут 10 с |
| Перехват кэша (`enableCacheInterception`) | выключен (по умолчанию) |
| Частота пересчёта | `revalidate = 60` в `src/app/layout.tsx` (все страницы), `300` на `/cases`, `3600` у sitemap |
| `limits.cpu_ms` в wrangler | не задан |
| Тариф Workers | **не проверен напрямую** (нужен дашборд Cloudflare; расширение Chrome отключено) |
| Размер серверного модуля Next | 5,4 МБ (`server-functions/default/handler.mjs`), модуль маршрутизации — 136 КБ |

## Что показали замеры (ПРОВЕРЕНО, логи 19 окт)

1. **Холодный старт под нагрузкой превышает лимит CPU.** Шесть параллельных запросов разных страниц: процессорное время 84, 160, 212, 230 мс у успешных; `/batch-photos` — **exceededCpu на 131 мс**. Повторный запрос в «тёплый» экземпляр — 3–64 мс. При обычном просмотре в браузере (страница подгружает данные ссылок) 5 из 23 страниц получили 503.
   - На платном тарифе лимит по умолчанию 30 000 мс; превышение на 131 мс означает лимит ниже этого, что соответствует **бесплатному тарифу (10 мс с небольшим допуском)**. ВЫВОД с высокой уверенностью.
   - Каждый запрос страницы загружает и выполняет 5,4-мегабайтный серверный модуль Next.js (`worker.js` → `import("./server-functions/default/handler.mjs")`), даже если ответ берётся из кэша. На новом экземпляре это и есть 84–230 мс.
2. **Фоновый пересчёт зависает.** Для `/services`, `/pricing`, `/about`, `/contact` HEAD-запрос пересчёта висел ~40 с (CPU 3–22 мс — процессор простаивает, ждёт ввода-вывода) и отменялся («waitUntil() tasks did not complete… cancelled»); родительский запрос логировал «TimeoutError» через 10 с. Для `/how-it-works`, `/why-ireland` пересчёт проходил за 0,15–0,8 с. `/pricing` в одном замере пересчиталась, через 3 с снова была STALE.
   - Внешние данные это не объясняют: Supabase отвечает за 0,14–0,31 с; `/services` и `/about` вообще не запрашивают данных. **Точная причина ожидания не установлена** — для неё нужны логи внутри рендера (Workers Logs в дашборде, observability включён).
   - Последствие: такие страницы остаются устаревшими, каждый визит запускает новый пересчёт и держит вызов Worker до 10 с — это добавляет параллельных вызовов и новых холодных стартов.
3. **Формы.** API-маршруты динамические, всегда загружают серверный модуль; на холодном экземпляре подвержены тому же превышению. `/api/partnerships` ответил 503 один раз и 400 (нормальная проверка полей) при повторе. Клиентская часть при 5xx показывает ошибку, сохраняет ввод и предлагает WhatsApp и телефон (тест `lead-failure-path`).
4. **Googlebot и браузер** получают одинаковые ответы (200, canonical, `index, follow`); логики по user-agent нет; hreflang на сайте нет (один язык).

## Предлагаемые изменения (код НЕ менялся — ждёт подтверждения)

**A. Перехват кэша OpenNext: `enableCacheInterception: true` в `open-next.config.ts`.** Готовые страницы и RSC-данные отдаются из KV на уровне модуля маршрутизации (136 КБ), серверный модуль 5,4 МБ для них не загружается. Ожидаемо — большое снижение CPU на попадание в кэш, в том числе на холодном старте (измерить до/после).
- Риски: опция помечена как «dangerous» (несовместима с PPR — PPR не используется; middleware нет); нужно проверить, что на перехваченных ответах остаются заголовки безопасности (CSP, HSTS) и редиректы; **перехватчик ждёт пересчёт устаревшей страницы** (`await queue.send`, до 10 с) — поэтому только вместе с B.

**B. Реже пересчитывать страницы: `revalidate` в `layout.tsx` 60 → 600 (раз в 10 минут, не час и не сутки).** Формы, заявки, админка, API — динамические и не кэшируются, их это не касается.
- **Исправление 20 окт:** ранее здесь было написано, что таблица акций (миграция 0007) не создана. Это неверно: в продакшене есть живая акция — баннер «Opening Soon — Ireland-wide E-commerce Fulfilment / View offer» (`/offers/1b83bde1-…`), текста нет в коде. Запись в `docs/PROJECT_STATUS.md` устарела.
- Поэтому не час: страницы собираются на машине без доступа к базе, и сразу после деплоя идут без баннера до первого пересчёта (проверено на предпросмотре: на кандидате баннера нет, на продакшене есть). 10 минут ограничивают этот разрыв и задержку изменений акции.
- Риски: изменение или окончание акции видно на сайте с задержкой до 10 минут; после деплоя баннер отсутствует до 10 минут.

**C. Не трогать:** тексты, `/videos`, SEO-разметку, canonical, sitemap. Фоновую подгрузку ссылок (prefetch) пока не отключать: после A эти запросы обслуживаются из кэша дёшево; отключать только если замер после A покажет всплески.

**Что кодом не исправить:** холодный старт API форм на бесплатном тарифе (они всегда загружают сервер Next). Полностью устраняет только Workers Paid.

## Проверка после реализации (план)

Предпросмотр Worker → тот же сценарий запросов с `wrangler tail`: последовательный обход 23 страниц, браузерный просмотр на 375 px и 1366 px, всплеск 6 параллельных запросов × 5; сравнить CPU p50/p95/max, число `exceededCpu`, долю 503, наличие CSP/HSTS, canonical, редиректов; формы — только пустыми/невалидными запросами (без настоящих заявок); полный набор тестов и сборка. Откат — мгновенный: `npx wrangler rollback <предыдущая версия>`.
